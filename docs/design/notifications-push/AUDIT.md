## Detail

### F1 (high) Watchdog 'new' cursor drops properties whose match facts arrive late, and floods alerts when a paused watchdog is switched back on

`api/notifications.py:1309`

match_once moves each subscription's cursor (last_matched_first_seen_at) to the newest first_seen_at among the properties that match at pass time. Because the dedupe key fires once ever, a property the cursor has already passed gets one more chance only: the lookback, which covers 60 min and runs only while the image gate is on. Match facts often arrive later than that, the served-location predicate (line 257) above all. For any broad spec, a property that starts matching after a later-seen match has moved the cursor is therefore never alerted, and with the gate off there is no second look at all. Separately, update_subscription never resets the cursor, and only active subscriptions advance it. A watchdog paused for N days and switched back on therefore emits every match from those N days, up to 1000 per 5-min pass, and a new watchdog bursts its 24 h backfill (migration 059 default). The bell can absorb that; on push it is a flood.

**Failure scenario.** A broad watchdog (byt, pronajem, Praha). Property P is first seen at 10:00, but its location resolves at 11:30. Meanwhile properties first seen at 10:05 and later match and move the cursor past 10:00. At 11:30 P matches, but first_seen_at <= cursor and first_seen_at is older than now()-60min, so neither query selects it and no alert is ever written. Second case: a user pauses a watchdog for a week, then resumes it. The next passes dispatch about a week of matches, 1000 per pass, and with push each one is a device notification.

**Proposed fix.** Delete the cursor model. Drop last_matched_first_seen_at, notifications_match_window_listings, MatcherSettings, Phase 1 (upper) and Phase 3 (advance), and the separate lookback branch. Replace them with ONE gated INSERT per subscription over a fixed window: first_seen_at > now() - interval '24 hours' (live: 35 of 31,214 properties served later than 24 h). The once-ever dedupe_key stays the only idempotence. This bounds a resume or a create to a 24 h backfill and gives every late fact 24 h. Semantics note: a property under 24 h old that starts matching later fires 'new' (true today within 60 min). Whether a backfill should reach push is a delivery ruling.

### F2 (high) Outbox has no lease: a deploy strands claimed sends forever (lost), and overlapping drains double-send retries

`api/channel_client.py:83`

ChannelClient.send works in three steps. It commits a 'queued' claim, then calls the transport, then finalizes. The NEW pass treats ANY ledger row as handled (anti-join on dedupe_key), and the RETRY pass reads only status='failed'. A process that dies between claim and finalize therefore leaves a 'queued' row that no query ever reads again: the event is never delivered, and nothing records the loss. That death happens on every deploy. The API service sets no drainingSeconds (Railway's documented default is 0 s between SIGTERM and SIGKILL; the worker sets 30), so the lifespan's 10 s task join never runs. Separately, the RETRY pass takes no claim. Two drains running together (Railway overlaps the old and new deployment) both select the same due 'failed' row and both send it. Resend calls carry no idempotency key, and push has no server-side dedup. The design calls this 'restart-safe'; it is at-most-once with silent loss, plus duplicate sends on retry.

**Failure scenario.** The outbox is mid-pass with 40 pushes claimed in sequence when a PR merges. Railway SIGKILLs the old container. The row being sent stays 'queued' forever, and the user never gets that alert. In another deploy, old and new containers overlap for a few seconds, and both run the retry pass on a row whose next_attempt_at is due. Both call the transport, and the device shows the alert twice.

**Proposed fix.** Use one leased state machine instead of claim, then send, then finalize. The claim INSERTs the row as due-later (status 'failed' or 'pending', next_attempt_at = now() + a 2-min lease). One 'due' pass takes rows with UPDATE ... SET next_attempt_at = now() + lease WHERE id = ANY(...) AND next_attempt_at <= now() AND attempts < max RETURNING id (a CAS claim), sends them, and finalizes. A crashed send simply becomes due again, and two drains can never both win the CAS. This deletes the never-read 'queued' semantics, the separate RETRY branch (its duplicate SELECT, row unpacking and compose call) and the unreachable TransportError branches. Optionally add drainingSeconds to railway.json so SIGTERM is honoured.

### F3 (high) Every account's opted-in alert goes to ONE global operator address, and never to the account that opted in

`api/notification_outbox.py:144`

Delivery reads the recipient from global app_settings (notification_email_to, notification_telegram_chat_id) and ignores dispatch.account_id. Any tenant can opt a source into a channel: the picker is shown to every user, the API takes any string, and the browser role can also write those columns directly through PostgREST. Once a transport and the operator's recipient are set, tenant B's matches (listing, price, place, deep link) are sent to the operator's inbox. B gets nothing, and the ledger records 'sent'. This is dark today only because nothing is configured.

**Failure scenario.** The operator turns email on for himself: RESEND_API_KEY + EMAIL_FROM, plus notification_email_to = his address. Tenant B earlier ticked Email on the watchdog '3+kk Brno do 8M' in CreateWatchdogModal. On every 300 s matcher pass B's new matches are stamped target_channels={email}. The 120 s outbox resolves the single operator address, so the operator receives B's private search results. B receives nothing, and channel_sends says 'sent', so any later per-account delivery metric is wrong.

**Proposed fix.** Subtract routing from the producers and resolve the recipient per account at delivery. Delete notification_subscriptions.channels, collections.notify_channels, app_settings.system_health_channels, notification_dispatches.target_channels, app_settings notification_email_to and notification_telegram_chat_id, _RECIPIENT_KEYS/_resolve_recipient, DeliveryChannelsPicker with its 3 mounts, and Settings > Delivery (all via forward migrations). Delivery then becomes `dispatch JOIN push_subscriptions ps ON ps.account_id = d.account_id WHERE d.source_kind IN ('watchdog','collection_monitor','share')`, and later email goes to the account's own verified address. The SYSTEM account has 0 members, so system_health rows reach no device by construction, which matches the operator's 'watchdog, monitoring, shared only'. One per-account preference replaces three per-source arrays.

### F4 (high) Dispatch 'Estimate rent' route reads any account's estimation run by serial id, and files tenants' runs under SYSTEM where every tenant can read them

`api/routes/notifications.py:198`

POST /notifications/dispatches/{id}/estimate runs on the service-role connection behind require_token. _fetch_dispatch has no account predicate and LEFT JOINs estimation_runs without RLS. The browser role may UPDATE notification_dispatches.estimation_run_id on its own rows; this is a column grant, and the foreign-key check ignores RLS. A tenant can therefore point its own dispatch at any bigint run id and have the route return that run's result fields. Separately, the kickoff hand-INSERTs estimation_runs without account_id. The column DEFAULT stamps those rows SYSTEM, and estimation_runs_tenant_read shows SYSTEM rows to every account, so tenant A's dispatch estimate (subject listing, input_spec lat/lng, result) becomes visible to all tenants. Roadmap item 11 already lists the route as account-blind; the serial-id read chain and the SYSTEM publication are not recorded there.

**Failure scenario.** Tenant B has one dispatch of its own (any watchdog match, or a share sent to B). B runs PATCH /rest/v1/notification_dispatches?id=eq.<own> {"estimation_run_id": 1234}; the tenant_update policy and the column grant both pass. B then calls POST /notifications/dispatches/<own>/estimate. The service role joins run 1234 unscoped and returns another account's estimated rent, sale price, yield and confidence. B loops over the id to enumerate runs. Second path: tenant A clicks 'Estimate rent' on /watchdog, and the run lands under account 0000…; every other account can now read it through estimation_runs and the estimates views.

**Proposed fix.** Delete the whole path. The property page already owns estimations through create_estimation_run (rule 12). Remove the route, kickoff_estimation_for_dispatch, _resolve_listing_for_estimate, _link_dispatch_run, _insert_pending_run, _insert_failed_run, run_pending_estimation (about 310 lines), the er.* projection and its LEFT JOIN, the SPA's kickoffWatchdogDispatchEstimate (api.ts:2847) and the Estimate-rent column. Then, in a forward migration, revoke UPDATE(estimation_run_id) from authenticated and drop notification_dispatches.estimation_run_id. Live it holds 0 non-null rows, but the drop is destructive, so it needs operator OK plus a backup. This also closes the notification entry of roadmap item 11 and the rule-12 fork.

### F5 (high) System notices fill the one feed and badge, nobody reads them, and bulk 'Mark all read' acts as a hidden acknowledge

`toolkit/system_alerts.py:132`

system_health is 902 of the 943 dispatches. Since July none has ever been seen, and no incident has been acknowledged since 619 added Acknowledge. The volume is about 15 a day (31 in the last 48 h, 344 in 30 d). Every notice carries the constant change_kind 'system_alert', so onset, reminder and recovery are told apart only by parsing the dedupe key, and that grammar has had at least four generations ('sys:ops_incident:<id>:onset', ':reesc:', 'onset:{iso}', 'reminder:{rung}:{iso}:{id}x{n}'). 798 of the 902 rows name a check key that is no longer registered, so the 'Open Health' anchor built from split_part(dedupe_key) points at nothing. Recoveries (82 of 344 in 30 d, 24%) get the same brick-red AlertIcon chip and count as unread alerts. unread_count adds up every source, so the admin badge reads 910 ('99+') and hides the operator's 8 real unread property alerts; an iOS app_badge built on this number would mean nothing. Separately, seen_at is a control input: the canary passes an open, unacknowledged alarm once its notice is 'read in the bell'. Reading never acknowledges (619:92-94), yet a bulk mark-all quietly turns off the one external escalation path. Checked against the reader's claim: admins CAN mark system rows seen. 619 added notification_dispatches_admin_update and it is live; the last bulk mark-all (2026-10-14) came before it. So the 99+ is volume nobody reads, not an RLS bug.

**Failure scenario.** The operator presses 'Mark all read' to clear 99+ before the sprint's push badge ships. That one UPDATE stamps every SYSTEM row seen (admin arm, 619:99-103). For the next 12 h the canary reads each open, unacknowledged alarm as 'handled' (health_canary.py:110) and sends no GitHub failure email, although nothing was acknowledged on Health. In the other direction, if the bell is left alone, the phone badge set from unread_count would show 99+ for ever and the 8 real Monitoring alerts would be invisible in it.

**Proposed fix.** Subtract system_health from notification_dispatches. ops_incidents already records onset (first_seen_at), notices (alert_count, alerted_at), recovery (resolved_at) and the acknowledgement, and Health shows them. Delete: the INSERT in emit_system_alert (the ladder keeps stamping alerted_at), _system_health_channels plus its app_settings key, the trigger's SYSTEM else-branch and both SYSTEM RLS arms (364:47-50, 619:99-103), the check_key derivation, SystemNotificationRow and the System tab, the outbox's system branch and _SYSTEM_KEY, and the canary's seen/delivered arms. The canary then judges only 'open, unacknowledged past grace', which is the truth. The 902 rows go out in a backed-up destructive migration. This reverses ruling Q1 2026-10-18 (docs/design/health-dashboard.md:1478, 'bell only'), so it needs the operator's OK. If Q1 stands, the smallest subtraction is to stop emitting recovery notices (system_alerts.py:302-306 and the recovery emit after :404): resolved_at is already the record, and that removes 24% of the volume.

### F6 (high) Two definitions of event identity disagree: the dedupe_key embeds a property_id that merges change, and the carrier collapses distinct events as 'twins'

`toolkit/property_carriers.py:157`

A dispatch has two identities. (1) The insert-time string dedupe_key embeds property_id for new, inactive and reactivated ('wd:{sub}:new:{pid}', 'cm:{c}:inactive:{pid}:{epoch}', 'cm:{c}:reactivated:{pid}:{epoch}'). A merge re-points the property_id column but never the key; 206 calls the key 'stable', i.e. stale by design. (2) The merge carrier treats rows as twins when they match on (subscription_id, collection_id, change_kind, trigger_snapshot_id). trigger_snapshot_id is NULL for new, inactive, reactivated and new_source, so any two events of the same kind under one source count as twins whatever their time or introducing ad. The collapse then DELETEs the retired one. The carrier has no `at`, so the delete leaves no carry record. Neither identity is correct for snapshot-less kinds. new_source also keys on two id spaces (sreality_id, or 'l'||listing_id).

**Failure scenario.** Two portal copies of one flat, A and B, are both in a monitored collection. A went inactive on 10-01 ('cm:c:inactive:A:t1'); B went inactive on 10-05. Autodedup merges A into B. The collapse deletes A's Delisted event because it matches B's (c, 'inactive', NULL) row, so a real event vanishes from the 'append-only' table with no trace. Alternatively, with A's row moved onto B: if B's newest inactive_at is still t1 inside the 7-day window, the monitor computes 'cm:c:inactive:B:t1'. The key differs, so the INSERT succeeds and the same flip is told twice; under push that is an irreversible duplicate notification. The watchdog 'new' key hits the same re-fire whenever the survivor still falls in the matcher's lookback.

**Proposed fix.** Keep ONE identity: structured columns plus one unique index, used by both the producers' ON CONFLICT and the carrier's collapse. Replace the text dedupe_key with an event_ref column (the snapshot id for price, the flip epoch for lifecycle, the introducing listing id for new_source, NULL for new). Index (source_kind, subscription_id, collection_id, change_kind, property_id, event_ref) with NULLS NOT DISTINCT, and give the carrier exactly that tuple. That deletes the key grammar and every reader that parses it (feed split_part at api/notifications.py:500-503, outbox _SYSTEM_KEY, canary split). A merge collapses only true twins, and a re-fire after a merge hits the conflict.

### F7 (high) Three overlapping routing models decide 'where an alert goes': producer-stamped target_channels, three per-source channel arrays, and one global recipient

`api/notification_outbox.py:43`

Delivery routing is stored at three layers. (1) Every producer copies a free-form channel list into notification_dispatches.target_channels, at seven INSERT sites. (2) That list comes from one of three per-source stores: notification_subscriptions.channels (mig 208), collections.notify_channels (mig 211) and app_settings.system_health_channels (mig 274). The SPA edits the first two with one picker mounted in three places, and the API carries them through curation and act-as plumbing. (3) The outbox then ignores account_id and resolves ONE global recipient per channel from app_settings (notification_email_to / notification_telegram_chat_id), which an admin-only Settings > Delivery form edits. Rule 16 says delivery is separate from detection, yet delivery policy is stamped onto the event row. The layers also disagree: the watchdog strips 'in_app' and the collection monitor does not, and nothing validates the vocabulary. The model as built is single-operator. Push needs a per-account (per-device) recipient, so this model cannot carry it and would sit beside it as a second routing system.

**Failure scenario.** Tenant B (one of 7 accounts) ticks 'Email' on a watchdog, which the picker offers to every user and the API accepts unvalidated. The operator later sets RESEND_API_KEY and notification_email_to for their own alerts. On the next drain, B's matches, with B's listing details, are emailed to the operator's address. B gets nothing, and nothing errors. A channel name that is typo'd or removed (e.g. 'telegram' after its transport goes) also silently drops out at `ch = ANY(configured)`. If push is added next to this model, a third recipient path appears.

**Proposed fix.** Make producers detection-only and resolve delivery at drain time from d.account_id. Delete target_channels: the column, all seven stamping expressions, the feed projection at notifications.py:506 and the SPA type field at types.ts:1177. Delete notification_subscriptions.channels, collections.notify_channels, app_settings.system_health_channels/notification_email_to/notification_telegram_chat_id, _system_health_channels, _RECIPIENT_KEYS/_resolve_recipient, DeliveryChannelsPicker with its three mounts, Settings > Delivery, and the notify_channels arm of refuse_monitoring_while_acting. Replace them with one per-account preference (in-app always; push = this account's registered devices; email = the account's sign-in address, off while email is inactive). The drain joins dispatch → account → its endpoints. The new part is a push_subscriptions table and one preference; it removes 3 columns, 3 settings, 1 component, 1 settings section and about 10 code sites. Cost: per-watchdog and per-collection channel choice goes away, a UX change that has 0 live users; consult the operator. test_notification_outbox's app_settings recipient fake and the channel-stamping pins in test_notifications/test_curation/test_pipeline_shares have to be rewritten. The column drops are destructive, so they need the rule-1 gate (pause + backup), though every value is empty.

### F10 (high) Delivery is at-most-once with silent loss on every API process death; Railway kills the API with no draining

`api/channel_client.py:83`

ChannelClient.send commits a 'queued' claim row, calls the transport, and only then finalizes it. Neither outbox pass ever reads a 'queued' row: NEW anti-joins on the row existing, and RETRY selects status='failed' only. So a process that dies between claim and finalize leaves the alert neither sent nor retried, permanently and without a trace. This is not a rare crash path. The API's railway.json sets no drainingSeconds, so Railway's default of 0 s applies (SIGKILL right after SIGTERM). The worker fixed this same Railway behaviour for itself (E941, drainingSeconds 30). The lifespan's 10 s graceful wait also cannot stop the drain thread. On top of that: drain_once has no per-row try/except, so one finalize or claim error aborts the whole 200-row pass. The RETRY pass takes no claim, so the ~20 s deploy overlap of two instances can double-send a due failed row. The docstring's 'restart-safe' claim is false. Push makes this worse: one dispatch fans out to N devices, so a pass covers more sends.

**Failure scenario.** Push is on and a watchdog match fans out to 3 devices. The outbox is mid-pass on a slow APNs POST when a PR merges (about 20 a day). Railway SIGKILLs the old container at once. The row for device 2 stays 'queued' forever, and devices 2 and 3 never get the alert. Nothing reads 'queued' and no Health cell counts it, so the ledger shows a send that is neither sent nor failed. In a separate case, a transient pooler drop during _finalize raises out of drain_once. The rest of the 200 rows wait for the next pass, and the row whose push already went out stays 'queued' (delivered, but recorded as never sent).

**Proposed fix.** Use one claim-and-lease state machine on the ledger with no new column. Write the target rows as 'queued' with next_attempt_at=now() at fan-out. Each pass claims with UPDATE ... SET next_attempt_at = now() + interval '2 min', attempts = attempts + 1 WHERE id IN (SELECT id FROM channel_sends WHERE status IN ('queued','failed') AND next_attempt_at <= now() AND attempts < max FOR UPDATE SKIP LOCKED LIMIT n) RETURNING ..., so a killed send comes back by itself after the lease. Put a try/except per row and check stop_event between sends. Pass the provider idempotency key (the dedupe_key) so an at-least-once resend is harmless. This merges NEW and RETRY into one query and deletes the RETRY pass, ChannelClient.retry, the computed-key anti-join ('notif:'||id||':'||ch) and the 'restart-safe' prose. Also set drainingSeconds on the API, or better, host delivery in the worker (see the hosting finding).

### F11 (high) SPA_BASE_URL is not set on the Railway API service, so every external message would carry a relative link

`api/notification_outbox.py:63`

compose_message builds every deep link as f"{_spa_base()}/listing/...", and _spa_base() defaults to ''. The pwa reader left open whether SPA_BASE_URL is set on the API service. ### F12 (medium) Matcher lease is stranded on every deploy, so all producer passes stall up to about 20 min while liveness reads 'held'

### F28 (medium) Feed rows link by the legacy sreality_id, which breaks for non-sreality ads, while the outbox builds a second, different link for the same dispatch

`frontend/src/pages/Notifications.tsx:273`

The dispatch is property-grain (rule 16), yet both feeds link with listingPath(d.sreality_id). The feed projection selects sreality_id twice (d.sreality_id and lp.sreality_id). dict(zip) keeps the later one, the listing's, which is NULL for non-sreality portals, so the link becomes /listing/null. One event gets two different destinations, neither of them the property page, and a push needs an absolute URL that works for every portal.

**Failure scenario.** A watchdog fires on a bazos ad. The user taps the row on /notifications and gets /listing/null, a dead page, even though the property exists. The same dispatch sent by email would open /listing/bazos/<native>, a different page.

**Proposed fix.** Link every property-grain row with propertyPath(d.property_id), since every such row has property_id. Delete both sreality_id columns from _DISPATCH_SELECT/_LISTING_PROJECTION and from the WatchdogDispatch type (along with the 'owed' comment). The outbox's push and email link use the same /property/{id} form, built absolute from one required base URL. That removes one identity, one duplicate column and one of the two link builders.
